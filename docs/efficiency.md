# 省时间与省 token：做可比较的实验

## 成本来自哪里

输入包括提示、历史、规则、被读取的文件、工具返回；输出包括回答与生成内容；推理也可能计入用量。模型、推理档位、缓存机制、工具和套餐规则影响实际成本。订阅额度不能直接换算为 token。

## 推荐取舍

- 简单且边界清楚：从默认或适当较低推理档开始；复杂排错再提高。各客户端可用项不同，不固定推荐某个模型名称。
- 复杂任务先短计划，避免大规模返工；小任务直接执行，避免计划本身的额外成本。
- 相关路径和精简错误优先；必要时扩大搜索。保留首个真实错误与调用栈，不截掉定位所需信息。
- 输出优先改动摘要、验证和限制；这只减少部分输出，不能保证总成本下降。
- 同一问题保留会话，目标切换时用准确短交接；频繁重开会重复定位与读取。
- Skills/MCP 按需要使用；删除重复指令或失效工具。并行适合独立任务，可能用更多 token 换时间。
- 保留项目必需检查；新改动、失败或未解决疑点出现时才重复/扩大验证。

从同一个干净快照开始，避免先后改动混在一起；使用同一模型和推理档，相同验收。

耗时包括失败尝试和返工。无法获得 token 就只报告耗时与轮次，不能据此宣称 token 省了多少。缓存/运行波动会影响结果，小样本只说明这几次；在至少三类代表任务上复测后再形成个人规则。不为凑数据重复执行昂贵任务。

不要用禁用验证、隐瞒失败、删除关键约束或无限循环“直到完美”的方式追求省用量。
