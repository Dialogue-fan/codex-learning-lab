# 游戏引擎分支

默认浏览器路线的目的是缩短安装时间，练习沟通与验证；不是所有游戏都应选浏览器。

| 路线 | 项目上下文需要给什么 | 最小任务 | 必要验收 |
| --- | --- | --- | --- |
| 浏览器 JS | HTML 入口、规则模块、运行命令、截图 | 暂停/冲刺/结算 | 页面交互、时间与状态重置 |
| Godot | 实际版本、project.godot、场景树、信号连接、脚本路径 | CharacterBody2D 的移动与冷却 | 引擎内运行、碰撞层、切换场景与重开 |
| Unity | 编辑器版本、场景、Prefab、脚本、Input System 版本 | 角色控制与 HUD | 编译、Play Mode、引用完整、生命周期 |

选择引擎后把第 03 课验收移植过去；先让 Codex 检查你提供的项目，不猜节点名、引擎 API 或安装路径。优先用引擎自带几何体与原创占位素材，记录外部资源的许可和来源。

## 游戏设计任务书

玩家目标、主要操作、核心循环、失败/成功条件、单局时长、关键信息展示、手感参数、首版范围。设计判断用试玩和明确指标解释；参数与规则尽量分离，便于一次改变一个变量。

## 交给 Codex 的引擎任务模板

项目版本：填写实测版本。相关场景/脚本：让 Codex 定位并确认。目标行为：填写。保留：现有输入映射/资源引用。验收：正常操作、异常输入、暂停、死亡、重开。引擎不能运行时明确报告静态检查的范围，请学习者执行 Play Mode，不能声称已玩测。

## 引擎专项怎样整合

当前有可运行的浏览器游戏起点；Godot/Unity 现有内容为迁移指南，不冒充已运行的原生示例。未确定引擎时先用浏览器完成共同能力；确定后记录实际版本、输入系统、场景/资源结构、运行及导出命令，将03、06、19、21、22的同一份验收映射过去，不为每个引擎重抄整套教案。

选型只问会改变项目的条件：目标平台、2D/3D、已有经验与资产、可用设备。先验证一个最小工程能运行和导出，再扩展。引擎专项需在选定实际版本后执行验证，当前不声称具备三套完整成品。
